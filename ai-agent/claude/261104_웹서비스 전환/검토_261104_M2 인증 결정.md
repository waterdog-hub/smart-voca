## 2. 주요 결정

표 전체는 이슈 #9에 있다. 되돌아볼 가능성이 큰 항목만 적는다.

### CSRF 토큰을 세션에서 파생
- **배경**: `GET /auth/session`은 CSRF 토큰을 돌려줘야 하는데, 설계는 해시만 저장하도록 정했다. 해시로는 원문을 돌려줄 수 없다.
- **대안**: (a) 원문 저장. DB 유출 시 토큰도 유출된다. (b) 조회할 때마다 새 토큰 발급. 탭이 여러 개면 먼저 연 탭의 토큰이 무효가 된다.
- **결정 근거**: 세션 값을 키로 한 HMAC으로 파생한다. 세션 값을 아는 서버만 계산할 수 있고 원문 저장이 필요 없다. 해시 비교는 설계대로 유지한다.

### 로그인 전 요청은 JSON만 허용
- **배경**: 가입, 로그인, 인증 확인은 세션이 없어 CSRF 토큰을 줄 수 없다. 공격자의 계정으로 피해자를 로그인시키는 로그인 위조가 가능한지 확인이 필요했다.
- **대안**: 로그인 전 임시 토큰과 임시 쿠키 발급. 구조가 복잡해진다.
- **결정 근거**: 다른 사이트의 폼은 `application/json`을 보낼 수 없고, `fetch`로 보내면 브라우저의 사전 확인에서 막힌다. `text/plain`과 폼 형식이 거절되는지 테스트로 고정했다.

### 이메일과 IP는 키를 쓴 해시
- **배경**: 데이터 모델은 "해시"로만 적었다. 키 없는 SHA-256은 IPv4 전체를 쉽게 계산해 되돌릴 수 있고, 이메일도 목록 대입으로 찾을 수 있다.
- **대안**: 일반 SHA-256 (처리방침의 "IP 원문 미저장" 취지에 못 미침).
- **결정 근거**: HMAC-SHA256에 `AUTH_HASH_KEY`를 쓴다. 키를 바꾸면 시도 기록만 초기화되어 교체 부담이 작다. 세션과 메일 토큰은 충분히 무작위라 키가 필요 없다.

### 메일 토큰은 URL 조각에 둠
- **배경**: `?token=`은 서버 접속 로그에 남아 배포 설계 §6.1 "메일 링크 값 기록 금지"에 어긋난다. GET 요청만으로 토큰을 소비하면 메일 보안 검사 프로그램이 링크를 미리 열 때 인증이 끝나 버린다.
- **대안**: 쿼리 문자열 + 프록시 로그 마스킹. 빠뜨릴 곳이 많다.
- **결정 근거**: `/verify-email#token=...`을 쓰고 화면 스크립트가 POST한다. 실제 서버 접속 로그에 토큰이 없음을 브라우저 점검으로 확인했다. 같은 탭에 새 링크를 붙여 넣는 경우도 `hashchange`로 처리한다.

### 운영 메일은 실패 처리
- **배경**: 발송 업체가 정해지지 않았다 (인수인계 §4.2). 콘솔 구현을 운영에서 쓰면 로그에 링크가 남는다.
- **결정 근거**: 운영의 기본 구현은 항상 `MailSendError`를 던진다. 조용히 링크가 로그에 쌓이는 것보다 실패가 드러나는 편이 안전하다. **M10 전에 실제 구현이 필요하다.**

## 4. 검증 기록

- 자동 테스트: 174개 통과 (기존 89개 + M2 85개). 기존 테스트 1개와 공용 도우미의 설정 값을 새 운영 필수 항목에 맞춰 고쳤다.
- 마이그레이션: 빈 DB에 `alembic upgrade head` 후 `alembic check` 변경 없음.
- 브라우저 점검: 임시 DB, 실제 uvicorn, 헤드리스 Chrome으로 가입 → 로그인 → 재발송 제한 → 인증 → 로그아웃 20개 항목 통과. 375px 폭에서 가로 스크롤 없음. 스크립트는 저장소에 넣지 않았다 (1회성, 임시 폴더).
- 브라우저 점검에서 발견해 고친 결함: 같은 탭에 새 인증 링크를 붙여 넣으면 `#` 뒤만 바뀌어 페이지가 다시 실행되지 않고 이전 결과가 그대로 남았다.

## 5. 남은 위험

이슈 #9 `알려진 위험` 참고. M7 이전에는 비밀번호 재설정이 없어, 다른 사람이 먼저 가입해 둔 이메일의 주인이 비밀번호를 되찾을 경로가 없다. 공개 전이므로 M7까지 허용한다.
