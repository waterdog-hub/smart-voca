## 2. 환경 구성

| 환경 | 용도 | 데이터 | 구성 |
|------|------|--------|------|
| 개발 (local) | 개인 개발·테스트 | SQLite 파일 또는 로컬 PostgreSQL, 테스트 데이터만 | 호스트에서 직접 실행 (CLAUDE.md 규칙) |
| 운영 (production) | 실제 회원 서비스 | 실제 회원 데이터 | 아래 §3 구성 |

- 개발 환경 데이터로 운영 데이터를 대체하지 않는다. 운영 데이터는 개발 환경으로 내려받지 않는다 (개인정보 최소화).
- 설정값은 환경변수로만 읽는다. `.env`는 Git에서 제외하고 `.env.example`만 커밋한다 (CLAUDE.md 규칙 5).

### 2.1 설정 항목 (환경변수 이름 예시)

| 이름 | 용도 | 비고 |
|------|------|------|
| `APP_ENV` | `local` / `production` | 운영에서만 API 문서(`/docs`) 끔 (API 설계 D-API07) |
| `DATABASE_URL` | DB 연결 | 운영 비밀값 |
| `PUBLIC_BASE_URL` | 메일 링크·소셜 콜백 주소 | 도메인 확정 후 설정 |
| `SMTP_*` 또는 `MAIL_API_KEY` | 메일 발송 | 운영 비밀값 |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | 구글 로그인 | 운영 비밀값 |
| `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET` | 카카오 로그인 | 운영 비밀값 |
| `SESSION_TTL_*` | 세션 기간 (14일 / 3일) | 인증 설계 §2.1 |

- 비밀값 관리: 운영 서버의 환경변수 또는 호스팅 업체의 비밀 저장소에만 둔다. 채팅·문서·로그에 쓰지 않는다.
- 비밀값이 노출되면 즉시 교체한다 (해당 제공자 콘솔에서 재발급 → 환경변수 교체 → 재배포). 교체 기록을 운영 일지에 남긴다.

## 3. 운영 구성

```
[사용자 브라우저]
      │ HTTPS (443)
[리버스 프록시: HTTPS 인증서, 보안 헤더, 요청 크기 제한, 기본 요청 횟수 제한]
      │ HTTP (내부)
[웹 앱: FastAPI + uvicorn 여러 프로세스]
      │
[PostgreSQL: 관리형 또는 별도 서버, 자동 백업 설정]

[메일 발송 서비스] ← 웹 앱이 API로 호출
[구글·카카오 로그인 제공자] ← 콜백 주소 등록
```

### 3.1 HTTPS 와 리버스 프록시 (D-OP01)
- 리버스 프록시가 인증서를 자동으로 받고 갱신하는 도구를 쓴다 (예: Caddy). 인증서 만료 사고를 줄이기 위해서다.
- HTTP 요청은 HTTPS로 넘긴다. HSTS 헤더를 켠다.
- 보안 헤더(CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`)는 인증 설계 §5 기준으로 프록시 또는 앱 중 한 곳에서만 설정한다. 두 곳에 같이 두면 값이 충돌한다.
- 요청 본문 크기 제한: CSV 가져오기 5MB (인증 설계 §5)와 맞춘다.

### 3.2 웹 앱 실행
- 배포 단위는 **컨테이너 이미지** 하나다 (D-OP02).
- 웹 앱은 무상태(stateless)로 만든다. 세션은 DB에 있으므로 프로세스를 여러 개 띄워도 된다 (인증 설계 D-A01).
- 시작 시 DB 연결을 확인하고, `GET /healthz`가 DB 연결 상태를 응답한다 (실패하면 `503`).

### 3.3 DB
- 운영은 **PostgreSQL**을 쓴다 (D-OP03). 데이터 모델 D-W02에서 "공개 전 전환 시점을 정한다"로 남긴 항목을 이 단계에서 확정한다.
  - SQLite는 여러 프로세스가 동시에 쓸 때 잠금이 생기고, 자동 백업 도구가 부족하다.
- 스키마 변경은 **마이그레이션 도구 (Alembic)** 로만 한다. 운영 DB를 손으로 고치지 않는다.
- 마이그레이션은 배포 전에 실행하며, 이전 버전 앱과 함께 돌아가도 깨지지 않게 "추가 → 옮김 → 삭제" 순서로 나눈다 (열 이름 변경을 한 번에 하지 않는다).

## 4. 메일 발송

- 인증 메일, 재설정 메일을 보내려면 **전용 발송 서비스**를 쓴다 (일반 개인 메일 계정은 발송 한도와 스팸 분류 문제가 있다).
- 발송 도메인에 SPF, DKIM, DMARC 기록을 설정해 스팸함으로 가지 않게 한다.
- 메일 본문은 템플릿으로 관리한다. 링크는 `PUBLIC_BASE_URL`에서 만든다.
- 발송 실패는 로그에 남기고, 사용자 화면에는 "메일 발송에 실패했습니다. 잠시 후 다시 시도하세요"를 보여준다 (인증 설계의 재발송 1분 제한과 함께).
- 메일 발송 업체는 개인정보 처리 위탁 대상이다 (§7 참조).

## 5. 백업과 복구

| 항목 | 설계 |
|------|------|
| 전체 백업 | 매일 1회 자동 실행 (DB 전체). 암호화해서 저장 |
| 보관 기간 | 최근 14일분 (제안). 오래된 백업부터 자동 삭제 |
| 보관 위치 | 운영 DB와 다른 저장 공간 (같은 서버에 두지 않음) |
| 복구 연습 | 분기마다 백업을 임시 DB에 복원해 확인. 결과를 운영 일지에 기록 |
| 탈퇴 회원 데이터 | 서비스 DB에서는 즉시 삭제. 백업에 남은 데이터는 보관 기간(14일)이 지나면 사라진다. 처리방침에 명시 (§7) |

- 백업 실패는 알림으로 알린다 (§6).
- CSV 백업 (기존 D-22의 `data/backup/`): 웹에서는 **회원이 직접 내보내기** (`GET /words/export`)로 대체한다 (API 설계 §3). 서버 쪽에 CSV 백업 파일을 쌓지 않는다.

## 6. 로그와 모니터링

### 6.1 로그
- 형식: JSON 한 줄. 시각, 수준, 요청 경로, 응답 코드, 소요 시간, 요청 번호.
- **기록하지 않는 것**: 비밀번호, 세션 값, 인증 토큰, 소셜 토큰, 메일 링크 값, 단어장 내용 전체 (인증 설계 §6).
- 기록하는 인증 이벤트: 로그인 성공·실패 (계정은 해시), 가입, 탈퇴, 비밀번호 변경, 잠금 발생.
- 보관 기간: 90일 (제안). IP 주소는 원문 대신 해시로 남긴다 (인증 설계 §6).

### 6.2 모니터링과 알림

| 점검 | 방법 | 알림 조건 |
|------|------|-----------|
| 서비스 살아 있음 | 외부에서 `/healthz`를 1분마다 확인 | 3회 연속 실패 |
| 오류율 | 5xx 응답 비율 | 5분 동안 5% 이상 |
| 백업 | 백업 작업 결과 | 하루라도 실패 |
| 인증서 | 만료 30일 전 | 만료 임박 |
| 디스크·DB 용량 | 사용률 | 80% 이상 |
| 로그인 잠금 급증 | 잠금 이벤트 수 | 1시간에 평소의 10배 (무차별 대입 의심) |

- 알림 수신 방법은 이메일 또는 메신저 (구현 때 선택).
- 오류 추적 도구를 쓰면 예외 내용을 보내되, 개인정보와 비밀값은 제외하도록 설정한다.

## 7. 개인정보 처리 (운영 전 필수)

공개 서비스 전에 아래를 **처리방침 문서**로 확정하고, 가입 화면에 링크한다 (화면 설계 P-03).

| 항목 | 내용 |
|------|------|
| 수집 항목 | 이메일, 표시 이름, 비밀번호 해시, 소셜 고유 번호, 학습 기록 (단어장, 진도, 시험 결과), 접속 기록 (IP 해시) |
| 수집 목적 | 회원 식별, 학습 기능 제공, 인증 메일 발송, 부정 접속 방지 |
| 보유 기간 | 회원 탈퇴 시 즉시 삭제 (백업은 14일 후 소멸). 접속 기록은 90일 |
| 처리 위탁 | 호스팅 업체, 메일 발송 업체, 소셜 로그인 제공자. 업체명과 위탁 업무를 명시 |
| 국외 이전 | 해외 호스팅·메일 업체를 쓰면 이전되는 항목과 나라를 고지한다. 국내 업체만 쓰면 해당 없음 |
| 정보주체 권리 | 열람, 정정, 삭제, 처리 정지 요청 방법 (계정 설정 화면 또는 이메일) |
| 보호책임자 | 이름(또는 직책)과 연락처 |

- 처리방침 문안은 법률 검토가 필요할 수 있다. 이 설계 문서는 항목만 정하고, 문안 작성은 별도 작업으로 한다.

## 8. 배포 절차

1. 변경을 `main`에 머지한다. 테스트(단위·API·화면 테스트)가 모두 통과해야 한다.
2. 컨테이너 이미지를 만들고 버전 태그를 붙인다 (예: 커밋 해시).
3. 운영 DB 백업을 먼저 확인한다 (당일 백업 성공 여부).
4. 마이그레이션을 실행한다. 이전 버전과 호환되는 변경만 한다 (§3.3).
5. 새 이미지를 배포한다. 프로세스를 하나씩 바꾸면서 `/healthz`를 확인한다.
6. 배포 후 확인 목록: 로그인, 단어 목록, 암기 카드 한 장, 시험 문제 생성.
7. 문제가 생기면 **이전 이미지로 되돌린다**. DB는 이전 호환 구조라 되돌려도 깨지지 않는다 (§3.3).

- 배포 기록은 운영 일지에 남긴다 (날짜, 버전, 변경 요약, 되돌림 여부).

### 8.1 개발 도구 변경
- 로컬 개발은 기존처럼 호스트에서 직접 실행한다. 운영 배포만 컨테이너를 쓴다 (D-OP02).

## 9. 호스팅과 비용 (사용자 결정 대기)

호스팅 방식과 예산은 사용자가 정할 사항이다. 아래 선택지를 비교한다. 요금은 결정 시점에 각 업체 공식 가격표로 확인한다 (이 문서에는 금액을 적지 않는다).

| 방식 | 장점 | 단점 |
|------|------|------|
| (가) 관리형 플랫폼 (컨테이너 배포 + 관리형 DB가 묶인 서비스) | 배포·백업·인증서가 기본 제공. 관리 부담 낮음 | 비용이 규모에 따라 올라감. 한국 리전 유무 확인 필요 |
| (나) 국내 클라우드 가상 서버 직접 운영 | 국내 리전, 개인정보 국외 이전 고지 부담 없음. 비용 예측이 쉬움 | 백업·보안 업데이트·장애 대응을 직접 해야 함 |
| (다) 해외 클라우드 직접 운영 | 선택지 많음, 저가 옵션 있음 | 국외 이전 고지 필요, 관리 부담 |

- 공통 필요 항목: **도메인 1개** (연 비용 발생), 메일 발송 서비스, 소셜 로그인 앱 등록 (구글, 카카오).

## 10. 설계 결정 (ADR 형식)

### D-OP01 HTTPS는 자동 인증서를 쓰는 리버스 프록시에서 종료
- **대안**: 앱이 직접 인증서 관리. 갱신 실패 위험이 커서 제외.

### D-OP02 배포 단위는 컨테이너 이미지
- **배경**: 운영 환경 차이를 줄이고, 되돌리기를 이미지 교체로 할 수 있게 한다.
- **대안**: 서버에 소스를 복사해 직접 실행. 되돌리기와 재현이 어려워 제외.
- **영향**: CLAUDE.md의 "컨테이너 미사용" 규칙은 **로컬 개발**에 한정하도록 바꿔야 한다 (승인 필요, §12).

### D-OP03 운영 DB는 PostgreSQL
- **배경**: 데이터 모델 D-W02의 "공개 전 전환" 항목.
- **결과**: 자동 백업, 동시 쓰기, 복구 연습이 쉬움.

### D-OP04 백업 보관 14일, 복구 목표 RPO 24시간 / RTO 4시간 (제안)
- **근거**: 학습 기록은 하루 단위로 쌓이므로 하루 손실은 감당 가능한 수준이다. 규모가 작아 4시간 안에 복구하는 것이 현실적이다.

### D-OP05 로그에 개인정보와 비밀값을 남기지 않음
- **근거**: 인증 설계 §6. 로그는 접근 권한이 넓어지기 쉬워 사고 시 노출 범위가 크다.

### D-OP06 마이그레이션은 호환 방식 (추가 → 옮김 → 삭제)
- **근거**: 배포 중 구버전과 신버전이 동시에 돌아도 DB가 깨지지 않게 한다. 되돌리기를 보장하기 위해서다.

## 11. 확정 사항 (사용자 답변, 2026-11-04)

1. **호스팅**: 관리형 플랫폼 (§9 (가)). 배포·백업·인증서를 업체가 기본 제공한다. 구체적 업체는 요금·한국 리전 유무를 공식 자료로 확인한 뒤 고른다 (D-OP07).
2. **도메인**: 없음. 새로 구입한다. 구입 전까지 `PUBLIC_BASE_URL`과 소셜 로그인 콜백 주소는 임시 값으로 둔다.
3. **DB 시작 시점**: PostgreSQL (D-OP03, 제안을 그대로 적용).

### D-OP07 관리형 플랫폼 채택
- **배경**: 사용자가 관리 부담이 적은 방식을 선택했다. 백업·인증서·배포가 기본 제공되면 §5, §3.1의 직접 구현 항목이 줄어든다.
- **대안**: 국내 클라우드 직접 운영 (국외 이전 고지 부담이 없지만 관리 부담이 큼), 해외 클라우드 직접 운영.
- **결과**: §5 백업과 §3.1 인증서 설정은 업체 기능을 쓰는 방식으로 바뀐다. 업체의 **백업 보관 기간, 복구 지원 범위, 백업 암호화 여부**를 선정 시 반드시 확인한다. 기본 보관 기간이 14일보다 짧으면 D-OP04와 처리방침 문구를 맞춘다.
- **유의**: 관리형 플랫폼이 해외 리전이면 국외 이전 고지가 필요하다 (§7).

### 남은 확인 사항
- 업체 선정 (요금, 한국 리전, 백업 정책 비교): 사용자가 공식 가격표를 보고 정한다. 금액은 이 문서에 적지 않는다.
- 도메인 구입 후 `PUBLIC_BASE_URL` 확정, 구글·카카오 로그인 앱 콜백 주소 등록.
