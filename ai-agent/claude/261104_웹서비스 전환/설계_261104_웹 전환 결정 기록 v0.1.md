## 1. 배경과 목표

- 현재: Windows 데스크톱(tkinter) 앱, CSV 파일 저장, 한 사람만 사용 (`docs/설계_261028_smart-voca 설계서 v0.7.md` 기준).
- 목표: 개인이 회원가입해 로그인하면 **각자의 단어장, 설정, 일차 진도, 학습 기록, 시험 기록**이 저장되는 공개 웹 서비스.
- 장기 목표: 상용화 수준 (보안, 개인정보 보호, 운영 절차 포함).

## 2. 확정된 사용자 결정 (2026-11-04)

| 항목 | 결정 | 비고 |
|------|------|------|
| 백엔드 | FastAPI + SQLite로 시작, 이후 PostgreSQL 전환 | SQLAlchemy 등 ORM을 쓰면 전환 비용이 낮다 (§3 D-W02) |
| 회원 인증 | 이메일·비밀번호 **와** 소셜 로그인 둘 다 | 단계 나누기 제안은 §3 D-W03 |
| 배포 범위 | 공개 인터넷 서비스 | 보안·개인정보 요구가 크게 올라감 (§3 D-W04) |
| 기존 데스크톱 앱 | 웹으로 대체 | tkinter 화면 코드는 유지보수 대상에서 빠짐 (§3 D-W05) |
| 단어장 소유 | 회원마다 자기 단어장 | 단어·진도·기록이 모두 회원에 속함. 공용 단어 목록은 쓰지 않음 (§3 D-W06) |

## 3. 결정 기록 (배경 / 대안 / 결정 근거)

### D-W01 웹 프레임워크 (사용자 확정: FastAPI)
- **배경**: 기존 코드는 Python 표준 라이브러리만 쓴다 (CLAUDE.md 기술 스택).
- **대안**: Django (인증·관리자 화면 내장), Flask (가볍지만 직접 조립할 것이 많음), 다른 언어 신규 작성.
- **결정 근거**: Python 자산(`src/core/`의 진도·시험·채점 로직)을 재사용하고, 학습 과정에서 구조를 직접 이해하기 쉽다. 자동 API 문서가 있어 설계 검증에 도움이 된다.
- **영향**: 외부 패키지 도입이 필요하다. CLAUDE.md의 "표준 라이브러리만" 규칙을 바꿔야 한다 (§5 승인 항목).

### D-W02 데이터 저장소 (사용자 확정: SQLite → PostgreSQL)
- **배경**: 현재 CSV 4~5종. 회원별 데이터 분리, 동시 접속, 트랜잭션이 필요해짐.
- **대안**: 처음부터 PostgreSQL, CSV 유지, SQLite 영구 사용.
- **결정 근거**: SQLite는 설정이 없어 시작이 빠르다. ORM으로 쓰면 PostgreSQL로 바꿀 때 연결 문자열과 일부 타입만 손보면 된다.
- **제약**: SQLite는 여러 프로세스가 동시에 쓰면 잠금 문제가 생긴다. 공개 서비스 전에 PostgreSQL 전환 시점을 정한다.

### D-W03 회원 인증 (사용자 확정: 이메일 + 소셜 둘 다)
- **배경**: 두 방식을 동시에 만들면 계정 연결(같은 사람이 두 방식으로 가입)과 이메일 인증 정책이 복잡해진다.
- **제안 (미확정)**: 1단계 이메일·비밀번호 가입과 로그인, 2단계 소셜 로그인 추가. 소셜 로그인 때 같은 이메일이면 기존 계정에 연결한다.
- **대안**: 처음부터 둘 다 구현, 소셜 로그인만 사용.
- **결정 근거(제안)**: 이메일 인증과 비밀번호 재설정은 두 방식 모두에 필요한 기반이라 먼저 만든다.

### D-W04 공개 서비스 요구 (사용자 확정: 공개 인터넷)
- **배경**: 불특정 다수의 개인정보(이메일, 학습 기록)를 받는다.
- **필요 항목 (초안)**:
  - 비밀번호는 해시(argon2 또는 bcrypt)로만 저장
  - HTTPS 적용, 쿠키 보안 옵션 (HttpOnly, Secure, SameSite)
  - CSRF 방어, 로그인 시도 횟수 제한
  - 비밀값(세션 키, DB 주소, 소셜 키)은 `.env`에 두고 Git에서 제외 (CLAUDE.md 규칙 5)
  - 개인정보처리방침 문안, 회원 탈퇴 시 데이터 삭제 절차
  - 백업과 복구 절차
- **결정 근거**: 공개 서비스는 기능보다 보안·개인정보 항목이 먼저 설계에 들어가야 한다.

### D-W05 데스크톱 앱 처리 (사용자 확정: 웹으로 대체)
- **배경**: 같은 기능을 두 벌 유지하면 기능 차이가 생긴다.
- **대안**: 둘 다 유지 (단어·설정 CSV를 웹과 주고받는 기능 추가).
- **결정 근거**: 데스크톱 앱은 기존 저장소로 두고 신규 기능은 웹에만 추가한다. 기존 CSV 가져오기 기능은 웹에서 한 번 쓰는 용도로 남길 수 있다 (§4 열린 질문).
- **재사용 대상**: `src/core/` 로직 (`day_planner`, `quiz_builder`, `answer_checker`, `word_service`). 저장 계층(`*_repository.py`)과 화면(`src/gui/`)은 교체 대상.

### D-W06 단어장 소유 방식 (사용자 확정: 회원마다 자기 단어장)
- **배경**: 데이터 모델의 최상위 소유자를 정해야 테이블 구조가 정해진다.
- **대안**: 공용 단어 목록 + 회원별 진도 (단어 중복 저장을 줄이지만, 한 회원이 단어를 고치면 다른 회원에게도 영향이 감).
- **결정 근거**: 회원 데이터가 전부 `user_id`로 묶여 구조가 단순하다. 단어 수정·삭제가 다른 회원에게 번지지 않는다. 같은 단어가 회원 수만큼 저장되는 비용은 학습 규모에서 무시할 수준이다.
- **영향**: 회원 탈퇴 시 해당 회원의 단어·진도·기록을 함께 삭제하면 된다 (§4-4와 연결).
