## 1. 개요 (Introduction)

### 1.1 개발방법론의 의미

시스템 개발방법론은 소프트웨어 공학 원리를 적용하여 정보시스템을 구축하는 과정에서의 작업 단계, 절차, 산출물 및 관리 체계를 표준화한 것이다. 이는 프로젝트 팀원 간의 원활한 소통을 돕고, 개발 품질의 상향 평준화를 보장하며, 유지보수의 효율성을 극대화하는 지표가 된다.

### 1.2 적용 방법

본 방법론은 프로젝트의 규모 및 특성에 따라 유연하게 적용(Tailoring)할 수 있다. 각 단계별 산출물은 다음 단계의 입력물(Input)이 되며, 특히 AI 에이전트와 협업하는 환경에서는 산출물의 텍스트 명확성과 추적성(Traceability)을 유지하는 것이 가장 중요하다.

### 1.3 본 환경 (aisw01) 기본 전제

- **운영자**: 한국어 사용자 중심 → 산출물·파일명·디렉토리명에 **한글 사용 권장** (§4.2)
- **AI 에이전트**: Claude (주, SSH 직접 접근), Gemini (보조, Antigravity 경유) — 상세는 §3.5

## 2. 개발 생애주기 및 산출물 (SDLC & Deliverables)

각 표의 "착수 시급성" 열은 프로젝트 단계별 산출물의 우선순위 가이드이다. 프로젝트 성격에 따라 테일러링한다.

- **1차** — 단계 진입 직후 착수 필요. `docs/` 로 가는 우선 대상
- **2차** — 해당 단계 진행 중 작성
- **선택** — 필요 시 혹은 운영 단계 진입 후

### 2.1 기획 단계 (Planning Stage)

프로젝트의 공식적인 승인과 비즈니스 목표 및 범위를 확정한다.

| :--- | :--- | :--- | :---: |
| **프로젝트 기획서** | **Project Charter** | 프로젝트 승인 정보, BRD(비즈니스 요구사항), SS(시스템 범위) 통합 | **1차** |

## 3. AI 에이전트를 위한 지침 (Guidance for AI Agent)

1. **추적성 준수 (Maintain Traceability):**
   - 모든 기능 구현은 `Requirement Spec`의 고유 ID와 연결되어야 한다.
   - 컴포넌트 간 통신 구현 시 반드시 `Integration Spec`에 정의된 데이터 규격 및 프로토콜을 준수한다.

2. **결정 근거 확인 (Consult Decision Records):**
   - 코드 생성이나 구조 변경 제안 전, `Decision Records`를 확인하여 특정 기술이나 패턴을 선택한 '의도'와 '맥락'을 파악한다.

3. **오류 분석 시 (When Analyzing Errors):**
   - 시스템 상호작용 오류 발생 시 `Architecture Design`과 `Integration Spec`을 대조하여 데이터 무결성과 통신 지점을 먼저 확인한다.

4. **문서 기반 소통 (Document-Driven Communication):**
   - 코드를 제안하기 전, 관련 설계 문서(`Process Logic` 또는 `Data Design`)의 최신 상태를 먼저 확인하고 변경 사항 발생 시 문서 업데이트를 병행한다.

5. **AI 에이전트 역할 분담 (본 환경 표준):**
   - **Claude** (주 에이전트):
     - 접근 방식: SSH 직접 접근 (aisw01 서버)
     - 주 역할: 코드 생성·수정, 설계·검토 문서 작성, Git 커밋/푸시, GitHub 이슈 관리, 테스트 실행
     - 작업 디렉토리: `ai-agent/claude/`
     - 운용 지침: 프로젝트 루트의 `CLAUDE.md` 준수 (문서 관리 규칙·디렉토리 명명·자동 실행 명령어 등)
   - **Gemini** (보조 에이전트, 사용 시):
     - 접근 방식: Antigravity 경유 (사용자 매개)
     - 주 역할: UI 디자인 탐색, 초안 생성 (분석·설계 문서의 대안)
     - 작업 디렉토리: `ai-agent/gemini/`
     - 협업 절차: Gemini 산출물은 Claude 가 검토 후 필요 시 `ai-agent/claude/yymmdd_주제/` 로 복사하여 작업 맥락에 편입

## 4. 파일 관리 규칙 (File Management)

### 4.1 표준 영문 네이밍 (참고)

국제협업·다언어 환경 전제. 본 환경에서는 §4.2의 한글 규칙을 기본으로 사용한다.

- **Naming Convention:** `{Project_Name}_{EN_Name}_vX.X_YYMMDD.md`
- **Example:** `ProjectA_Integration_Spec_v1.0_260404.md`

### 4.2 한글 네이밍 규칙 (본 환경 기본)

한국어 사용자가 주 운영자인 본 환경(aisw01)에서는 다음 한글 규칙을 채택한다. 문서명만으로 분류·주제가 즉각 식별되고, 분류 접두어 정렬로 주제별 묶임이 자연스럽기 때문이다.

- **문서명 규칙:** `분류_yymmdd_제목 vX.X.md`
  - `분류` ∈ {기획, 분석, 검토, 설계, 작업계획, 일지, 운영, 테스트, ...}
  - 예: `설계_260402_시스템 아키텍처 v1.0.md`, `분석_260416_AI API 16종 소스 상세 분석 v1.0.md`
  - 버전 업데이트: minor 증가 (v1.0 → v1.1 → v1.2). "버전 올리자" 요청 시 major 증가

- **디렉토리명 규칙:**
  - 참고자료 디렉토리: 날짜 없음, 단순 명쾌한 이름 (예: `uploads/`, `<원본명>/`)
  - 작업 기록 디렉토리: `yymmdd_주제/` (예: `260417_R_Python이식/`)
  - 로그성 예외: 주제명 단독 (예: `요청사항_로그/`)

- **문서 헤더 형식:** `파일 위치`, `작성일(YYYY-MM-DD)`, `버전`, `설명` 필수

- **포맷:** AI 에이전트와 인간 개발자의 가독성을 위해 Markdown 기본

### 4.3 테일러링 근거

- 분류(카테고리)를 접두어로 두면 파일명 정렬이 주제별로 묶이는 이점이 있다.
- 날짜를 `YYMMDD` 6자리로 두어 파일명 길이를 절감한다.
- 프로젝트별 추가 테일러링이 필요한 경우 해당 프로젝트의 `CLAUDE.md` §문서관리 규칙에 명시한다.
