# smart-voca 웹 서비스 — API 설계

**파일 위치**: `docs/web/설계_261104_API 설계 v0.8.md`
**작성일**: 2026-11-04
**버전**: v0.8 (공용 단어장 반영)
**설명**: 회원·단어장·설정·진도·암기·시험 기능을 REST JSON API로 나누고, 권한·오류 형식·시험 정답 보호 규칙을 정리한 4단계 설계 문서

---

## 1. 전제와 공통 규칙

- 결정 기록, 데이터 모델, 인증·보안 설계의 최신 확정 사항을 따른다.
- 기존 핵심 로직(`src/core/`)의 기능을 API로 옮긴다. 화면 흐름은 5단계(화면 설계)에서 정한다.
- 기본 경로: `/api/v1`. 모든 요청·응답은 JSON (`application/json`, 단어장 가져오기·내보내기만 예외).
- 날짜·시각은 ISO 8601 UTC 문자열 (`2026-11-04T06:30:00Z`). 화면에서 한국 시간으로 바꾼다 (데이터 모델 D-W11).
- ID는 1 이상 2,147,483,647 이하의 정수다. 범위를 벗어나면 `400`이다. 다른 회원의 자원 ID를 넣으면 `404`를 응답한다 (D-A09).

### 1.1 인증과 권한 수준

| 수준 | 조건 | 대상 |
|------|------|------|
| 공개 | 로그인 불필요 | 가입, 로그인, 인증 메일 확인, 재설정, 소셜 시작·콜백 |
| 로그인 | 유효한 세션 쿠키 | 내 정보 조회, 로그아웃, 계정 설정 |
| 인증 완료 | 로그인 + `email_verified_at` 있음 | 단어·설정 쓰기, 진도 생성, 암기, 시험 (인증 설계 §3.4) |

- 로그인 상태만 있고 인증이 안 된 회원이 쓰기 요청을 보내면 `403 EMAIL_NOT_VERIFIED`.
- 읽기 요청(단어 목록, 진도 조회, 시험 기록 조회)은 로그인만 있으면 된다.

### 1.2 CSRF

- 상태를 바꾸는 요청(POST, PUT, PATCH, DELETE)은 헤더 `X-CSRF-Token`을 함께 보낸다 (D-A07).
- 토큰은 `POST /auth/login`과 `GET /auth/session` 응답으로 받는다. 로그인 세션마다 하나다.
- 토큰이 없거나 다르면 `403 CSRF_INVALID`.
- 세션이 없는 공개 POST(가입, 로그인, 인증 확인)는 토큰 대신 `application/json`만 받는다. 다른 형식은 `400 VALIDATION_FAILED` (인증 설계 D-A12).
- 쿠키나 CSRF 토큰이 담긴 응답(`POST /auth/login`, `GET /auth/session`)에는 `Cache-Control: no-store`를 붙인다.

### 1.3 오류 응답 형식

```
{ "error": { "code": "WORDBOOK_BUSY", "message": "잠시 후 다시 시도해 주세요.", "fields": {} } }
```

- `code`는 고정된 영문 값이라 화면이 분기에 쓴다. `message`는 사용자에게 보여줄 한글 문구다.
- `fields`는 입력 검증 오류일 때만 쓴다. 칸 이름과 안내 문구만 담고 입력값은 되돌리지 않는다 (비밀번호가 응답에 담기지 않게 함).
- `429`는 `retry_after`(초)를 본문과 `Retry-After` 헤더에 함께 넣는다.

| HTTP | code 예시 | 상황 |
|------|-----------|------|
| 400 | `VALIDATION_FAILED`, `TOKEN_INVALID` | 입력 형식·범위 오류, 인증 메일·재설정 링크의 만료·재사용 |
| 401 | `AUTH_REQUIRED`, `LOGIN_FAILED` | 로그인 필요, 로그인 실패 (이메일 존재 여부를 숨기려고 같은 코드) |
| 403 | `EMAIL_NOT_VERIFIED`, `CSRF_INVALID` | 권한 또는 CSRF 실패 |
| 404 | `NOT_FOUND` | 없거나 다른 회원의 자원 |
| 405 | `METHOD_NOT_ALLOWED` | 허용되지 않는 메서드 |
| 409 | `WORDBOOK_BUSY`, `PLAN_NOT_READY`, `PLAN_ITEM_NOT_CURRENT`, `TEST_ALREADY_SUBMITTED`, `TEST_EXPIRED`, `LAST_LOGIN_METHOD` | 상태 충돌. `PLAN_NOT_READY`는 `reason` 필드로 사유 구분 (아래 §5) |
| 413 | `FILE_TOO_LARGE` | 가져오기 파일 5MB 또는 5,000행 초과 |
| 422 | `TEST_NOT_POSSIBLE` | 단어 수 부족 등 시험을 만들 수 없음 |
| 429 | `RATE_LIMITED` | 요청 횟수 초과 |
| 503 | `MAIL_SEND_FAILED` | 인증 메일 재발송 실패. 가입은 메일 실패에도 `202`를 유지한다 (D-A04) |

### 1.4 목록 공통 규칙

- 목록은 `limit`(기본 50, 최대 200)과 `offset`으로 나눈다. 단어장은 수천 개가 될 수 있다.
- 응답 형식: `{ "items": [...], "total": 1988 }`.

## 2. 인증·계정 API

| 메서드·경로 | 권한 | 설명 | 주요 응답·규칙 |
|-------------|------|------|----------------|
| `POST /auth/signup` | 공개 | 가입 (이메일, 비밀번호, 표시 이름, 약관·개인정보 동의) | `202`, 중복 여부와 관계없이 같은 응답. 자동 로그인 없음. 신규면 인증 메일, 기존 회원이면 "이미 가입된 이메일" 안내 메일 발송 (인증 설계 D-A04). 동의 안 하면 `400` |
| `POST /auth/social/complete` | 가입 대기 | 소셜 가입에서 이메일 입력 (제공자가 이메일을 주지 않은 경우) | `202`, 인증 메일 발송. 인증이 끝나면 회원 생성 (데이터 모델 v0.2 §4.3). 가입 대기 세션이 없으면 `401` |
| `POST /auth/login` | 공개 | 로그인 | 세션 쿠키 발급. 실패는 `401 LOGIN_FAILED` (이메일 존재 여부 숨김). 잠금 중이면 `429` |
| `POST /auth/logout` | 로그인 | 현재 세션 종료 | `204`, 쿠키 삭제 |
| `POST /auth/logout-all` | 로그인 | 모든 기기 세션 종료 | `204`, 현재 세션도 종료 |
| `GET /auth/session` | 공개 | 현재 상태 확인 (로그인 여부, 인증 여부, CSRF 토큰) | 로그인 안 했으면 `{ "user": null }` |
| `POST /auth/verify-email` | 공개 | 인증 메일 링크 값 확인 | 토큰 만료·재사용은 `400 TOKEN_INVALID` |
| `POST /auth/resend-verification` | 로그인 | 인증 메일 재발송 | `202`. 가입과 합쳐 주소당 1분에 1회. 이미 인증한 회원은 메일 없이 `202`. 이전 링크는 무효가 된다 |
| `POST /auth/password-reset/request` | 공개 | 재설정 메일 요청 | 가입 여부와 관계없이 `202` 동일 응답 (D-A04) |
| `POST /auth/password-reset/confirm` | 공개 | 새 비밀번호 설정 | 성공 시 모든 세션 종료 |
| `GET /auth/social/{provider}/start` | 공개 | 소셜 로그인 시작 (`provider`: `google`, `kakao`) | 제공자 인증 페이지로 이동 (302). `state`, PKCE 값 발급 |
| `GET /auth/social/{provider}/callback` | 공개 | 제공자 콜백 | 계정 연결 규칙 (인증 설계 §4.2). 수동 연결이 필요하면 연결 화면으로 이동 |
| `POST /auth/social/{provider}/link` | 로그인 | 비밀번호 확인 후 소셜 계정 연결 | 확인 실패는 `401` |
| `DELETE /auth/social/{provider}` | 인증 완료 | 소셜 연결 해제 | 비밀번호가 없고 연결도 마지막이면 `409 LAST_LOGIN_METHOD` |
| `GET /me` | 로그인 | 내 정보 | 이메일, 표시 이름, 인증 여부, 연결된 소셜 목록 (제공자 쪽 고유 번호는 응답에 넣지 않음, 제공자 이름만) |
| `PATCH /me` | 인증 완료 | 표시 이름 변경 | |
| `POST /me/password` | 인증 완료 | 비밀번호 변경. 소셜 전용 계정은 현재 비밀번호 없이 새 비밀번호 설정 가능 | 비밀번호가 있으면 현재 값 확인. 성공 시 다른 세션 종료 |
| `DELETE /me` | 인증 완료 | 탈퇴 (비밀번호 확인, 소셜 전용 계정은 제공자 재로그인으로 확인) | 하드 삭제: 회원 데이터 전부 삭제, 세션 종료 (데이터 모델 v0.2 §4.4) |

### 2.1 로그인 실패 응답 규칙
- 잘못된 이메일과 잘못된 비밀번호를 같은 `LOGIN_FAILED`로 응답한다.
- 응답 시간 차이를 줄이기 위해 존재하지 않는 이메일도 해시 검증 시간을 쓴다 (구현 시 확인).

## 3. 단어장 API

회원은 단어를 직접 추가·수정·삭제하거나 CSV로 가져오고 내려받지 못한다 (D-WB04). `POST /words`, `PATCH /words/{id}`, `POST /words/delete`, `POST /words/import`, `GET /words/export`는 없다(404 또는 405). 운영자가 단어장을 준비하고 회원은 담고 제외한다 (이슈 #17).

| 메서드·경로 | 권한 | 설명 | 주요 규칙 |
|-------------|------|------|-----------|
| `GET /wordbooks` | 로그인 | 공용 단어장 목록 | 응답 `items`: `{ id, title, description, source_note, word_count, sample_words(앞 5개), added, added_at }`. `id` 순 |
| `POST /wordbooks/{id}/add` | 인증 완료 | 단어장 담기 | 응답 `{ added, already_had }`. 살아 있는 같은 단어는 건너뛰고 뜻을 유지한다. 삭제된 같은 단어는 되살려 `id`와 기록을 잇는다 (데이터 모델 §4.5). 두 번 보내도 안전하다 |
| `POST /wordbooks/{id}/remove` | 인증 완료 | 단어장 제외 | 응답 `{ removed, kept }`. 다른 담은 단어장에 없는 단어만 소프트 삭제하고 진도에서 뺀다. 담지 않은 단어장은 변화 없이 `0, 0` |
| `GET /words` | 로그인 | 내 단어 목록 (읽기 전용) | 쿼리: `q`(단어·뜻 검색), `sort`(`word`, `meaning`, `created`), `order`(asc/desc), `limit`, `offset`. 기본은 `word` 오름차순이고, 값이 같으면 `id` 순이다. 삭제되지 않은 단어만 |

- 없는 단어장이나 범위를 벗어난 `id`: 없으면 `404`, 범위 밖이면 `400`.
- 담기·제외가 같은 회원의 요청과 겹쳐 제약에 걸리면 모두 되돌리고 `409 WORDBOOK_BUSY`다 (D-WB11).
- 단어장 등록은 API가 아니라 운영자 명령줄 도구다 (`ai-agent/scripts/load_wordbooks.py`, `data/wordbooks.json`, D-WB05). 파일은 5MB, 5,000행 이하, 단어 100자, 뜻 500자 이하이며 첫 줄은 `word,meaning`이다. UTF-8(BOM 포함) 후 CP949 순서로 읽는다. 읽을 수 없으면 도구가 오류로 멈추고 기존 단어장은 그대로 둔다.
- 기존 D-22(가져오기 전 자동 백업)는 웹에서 쓰지 않는다. 서버 DB 백업으로 대신한다 (결정 기록 §5a). 회원이 단어를 직접 바꾸지 않으므로 회원 CSV 백업도 없다.

## 4. 설정 API

| 메서드·경로 | 권한 | 설명 | 주요 규칙 |
|-------------|------|------|-----------|
| `GET /settings` | 로그인 | 설정 조회 | 회원 가입 때 만든 기본값 |
| `PUT /settings` | 인증 완료 | 설정 전체 저장 | 허용 값과 범위 검사 (D-23). 벗어나면 `400` + `fields`. 응답은 저장된 설정 |

- 요청과 응답의 칸은 `daily_new_count`, `daily_review_count`, `daily_wrong_count`, `wrong_threshold`, `test_format`, `test_direction` 6개다. 저장은 전체 교체이므로 6개를 모두 보낸다.
- 숫자 범위: `daily_new_count`와 `wrong_threshold`는 1~9999, `daily_review_count`와 `daily_wrong_count`는 0~9999다. JSON 정수만 받는다. `"5"`, `true`, `1.5`는 `400`이다.
- `current_day`와 `memorize_cursor_item_id`는 클라이언트가 보낼 수 없다. 요청에 있으면 무시하지 않고 `400`으로 거절하며, 응답에도 넣지 않는다. `current_day`는 서버만 진도 생성 때 바꾼다 (데이터 모델 D-W10). `memorize_cursor_item_id`는 쓰지 않는다 (§5).

## 5. 진도 API (일차별 진도, 암기)

| 메서드·경로 | 권한 | 설명 | 주요 규칙 |
|-------------|------|------|-----------|
| `GET /plans` | 로그인 | 일차 목록 (일차별 요약: 단어 수, 완료 수) | 지난 일차 보기 (F-11, D-16) |
| `GET /plans/{day}` | 로그인 | 한 일차의 항목 (단어, 뜻, 유형 new/review/wrong, 완료 여부, 순서)와 `is_current` | 읽기 전용. `position` 순. 항목이 없으면 `404` |
| `POST /plans` | 인증 완료 | 다음 일차 생성 (`current_day + 1`) | 생성 조건 미충족 시 `409 PLAN_NOT_READY`, 응답 `reason`: `NO_WORDS` (단어 없음) / `WRONG_THRESHOLD_NOT_MET` (오답 기준 미달) / `CURRENT_DAY_INCOMPLETE` (현재 일차 미완료). 옛 D-18의 사유 구분을 유지한다. 응답: 생성된 일차 |
| `PATCH /plan-items/{id}` | 인증 완료 | 암기 처리. 본문 `{ "done": true }` (외움) 또는 `{ "later": true }` (다시). 둘 중 하나만, JSON `true`만 받는다 | 현재 일차 항목만 바꾼다. 지난 일차는 `409 PLAN_ITEM_NOT_CURRENT`. `done`: `study_records.memorized_count` +1, `first_memorized_day`, `last_memorized_date` 갱신 (옛 설계서 6.4). `later`: 같은 일차 맨 뒤로 옮김, 기록 변화 없음 (옛 D-10 "다시" 규칙, 결정 기록 §5a). 이미 끝낸 카드는 바뀌지 않음 |
| `GET /progress` | 로그인 | 진행률 요약 (`total_words`, `memorized_words`, `current_day`, `day_total`, `day_done`) | 진행률 표시 (D-17). 삭제한 단어는 세지 않음 |

동시성 (2차 검토): 생성은 `settings.current_day`를 조건부로 올린다 (기존 값일 때만 `current_day + 1`로 갱신). 같은 요청이 동시에 두 번 들어오면 한쪽만 성공하고, 진 쪽은 `409 PLAN_NOT_READY` (`reason`: `CURRENT_DAY_INCOMPLETE`)를 받는다. 구현은 DB 트랜잭션에서 처리한다.

- 같은 항목에 `done: true`를 두 번 보내도 결과가 같아야 한다 (멱등). 카운트를 두 번 올리지 않는다.
- 카드 위치 복원 (D-10): 첫 번째 미완료 카드가 곧 이어 볼 카드다. 외움은 `done`, 다시는 `position`으로 저장되므로 별도 API를 두지 않는다 (2026-11-04 사용자 확정, 이슈 #14).
- 지난 일차 복습은 화면에서만 진행하고 API를 호출하지 않는다 (화면 설계 D-UI10).
- `PLAN_NOT_READY` 응답의 `reason`은 `error` 객체 안에 있다.

## 6. 시험 API

시험 문제에 정답이 들어 있으면 브라우저에서 정답을 볼 수 있다. 그래서 **정답은 서버에만 두고** 클라이언트에는 문제와 보기만 보낸다.

| 메서드·경로 | 권한 | 설명 | 주요 규칙 |
|-------------|------|------|-----------|
| `POST /tests` | 인증 완료 | 시험 시작. 형식·방향·문항 수를 받아 문제를 만든다 | 본문: `{ "test_format", "test_direction", "count" }`. 문항 수는 1~200이고, 단어 수보다 크면 단어 수만큼 낸다. 진행 중인 시험이 있으면 폐기한다. 단어가 부족하면 `422 TEST_NOT_POSSIBLE` |
| `GET /tests/{id}` | 로그인 | 진행 중인 시험 문제 조회 (새로고침 복원) | 문항 칸은 `id`, `position`, `direction`, `question`, `choices`뿐이다. 정답, 정답 번호, 단어는 빼고 응답한다 (뜻→영어 문항은 단어가 곧 정답이다). 제출했으면 `409 TEST_ALREADY_SUBMITTED`, 폐기됐으면 `409 TEST_EXPIRED` |
| `POST /tests/{id}/submit` | 인증 완료 | 답안 제출 | 본문: `{ "answers": [{ "item_id", "answer" }] }`. 객관식은 보기 번호(0부터, 정수만), 주관식은 문자열(500자까지). 답하지 않은 문항은 빼고 보낸다. 다른 시험의 문항이나 형식이 틀린 답이 있으면 전체를 `400`으로 거절한다. 채점은 서버에서 한다 (설계 6.3) |
| `GET /tests/history` | 로그인 | 시험 기록 목록 + 전체 정답률 | `limit`, `offset`. 응답: `items`, `total_count`, `overall_percent`. 정답률은 서버에서 계산하며 문항 수로 가중한다 (D-19) |

- 시험 한 세트는 제출될 때 한 번만 기록된다 (D-15). 같은 시험을 두 번 제출하면 두 번째는 `409 TEST_ALREADY_SUBMITTED`.
- 제출 결과 응답: 문항별 정답 여부와 정답 (제출 후에만 정답을 보여준다), 총점. 오답이면 `study_records.wrong_count` +1, `last_wrong_date`는 한국 날짜 (D-11).
- 답하지 않은 문항은 점수에서 오답이지만 `wrong_count`를 올리지 않는다. 풀지 않은 단어는 틀린 증거가 아니고, 일찍 제출해도 다음 진도가 왜곡되지 않아야 한다 (2026-11-04 사용자 확정, 이슈 #15).
- 문항별 결과는 제출 응답으로만 제공한다. 답안을 저장하지 않으므로 다시 조회할 수 없다 (데이터 모델 §7).
- 시험을 시작만 하고 제출하지 않으면 시작 후 24시간 뒤 폐기한다 (§10-2). 예약 작업 없이 조회와 제출 때 `expires_at`으로 판단한다. 쌓인 행의 정리는 M10에서 다룬다.

## 9. 설계 결정 (ADR 형식)

### D-API01 REST JSON + `/api/v1` 경로
- **배경**: 화면이 브라우저 자바스크립트다. 자원 중심 URL이 권한 규칙을 이해하기 쉽다.
- **대안**: GraphQL (학습 규모에 비해 복잡), 화면 중심 RPC (재사용 어려움). 제외.

### D-API02 정답은 서버에만
- **근거**: 브라우저 개발자 도구로 정답을 볼 수 있으면 시험이 의미가 없다.
- **결과**: 시험 문제를 DB에 저장해야 한다 (§8-1, §8-2). 시험 한 번당 행 몇 개가 추가된다.

### D-API03 목록은 페이지 단위
- **근거**: 단어장은 수천 개다. 한 번에 다 보내면 느리다.
- **결과**: 검색·정렬도 서버 쿼리로 처리한다.

### D-API04 쓰기 요청은 인증 완료 회원만
- **근거**: 인증 설계 §3.4의 확정 사항 (쓰기는 인증 후에만).

### D-API05 암기 완료는 멱등
- **근거**: 네트워크 재시도나 중복 클릭으로 카운트가 두 번 오르면 기록이 틀린다.

### D-API06 단어 삭제는 목록(`POST /words/delete`)으로 (폐기: D-WB04로 API 삭제)
- **대안**: `DELETE /words/{id}` 한 개씩. 기존 화면이 여러 개를 한 번에 지울 수 있어 목록 방식을 쓴다.
- **근거**: `DELETE`에 본문을 싣는 것은 일부 환경에서 막힌다.

### D-API07 API 문서 공개 여부
- FastAPI의 자동 문서(`/docs`)는 개발 환경에서만 켠다. 공개 환경에서는 끈다 (구조 노출 최소화).

### D-API08 입력 오류 형식을 직접 정의 (v0.2)
- **배경**: FastAPI 기본 `422` 응답은 입력값을 되돌려줘 비밀번호가 응답에 담기고, §1.3 형식과도 다르다.
- **결과**: `400 VALIDATION_FAILED`로 바꾸고 칸 이름만 알려 준다. `/api/` 경로의 `404`, `405`도 같은 형식으로 응답한다.

### D-API09 내보낸 파일은 다시 가져와도 값이 같다 (v0.3, 폐기: 내려받기 삭제)
- **배경**: 내보낼 때 수식 방지 접두 `'`만 붙이면 다시 가져올 때 `-ing`가 `'-ing`으로 바뀐다. 웹에서는 내보내기가 회원의 백업 수단이다 (결정 기록 §5a).
- **대안**: 내보낼 때만 처리 (왕복이 깨짐), 처리하지 않음 (수식 실행 위험).
- **결과**: 가져올 때 접두를 하나 뗀다. 원래 `'=`처럼 시작하는 값은 내보낼 때 `'`를 하나 더 붙인다.

### D-API10 가져오기는 데이터가 조용히 사라지지 않게 처리 (v0.4, 운영자 도구로 이동)
- **배경**: 데스크톱은 세 번째 열부터 버렸다. `run,달리다, 뛰다`의 뜻이 조용히 `달리다`로 잘린다. 한글 Excel의 기본 CSV 저장은 CP949지만 데스크톱은 `utf-8-sig`만 읽었다.
- **결과**: 뒤 열에 값이 있으면 줄 번호로 알리고 건너뛴다. Excel이 만든 빈 열은 허용한다. CP949도 읽되 UTF-8을 먼저 시도해 기존 파일 동작은 같다.

## 10. 열린 질문

1. **시험 진행 중 설정 변경**: 시작 시점의 형식·방향·문항 수로 채점한다 (데이터 모델 v0.2 `test_attempts`에 저장). 채택.
2. **시험 폐기 시간**: 시작 후 24시간. 폐기된 세트는 `expired`로 바꾼다. 채택.
3. ~~카드 위치 저장~~ → 처음에 채택했으나 M5에서 철회. 순서와 완료 여부로 복원한다 (§5).
