**버전**: v1.0 (docs로 승격)
**설명**: 공용 단어장(MW), 계정(M7), 소셜 로그인(M8), 디자인 개편에서 내린 결정 D-WB, D-M7xx, D-M8xx, D-DS의 대안과 이유를 한곳에 모은 아키텍처 결정 기록. 설계 문서들이 인용하는 번호의 정의가 여기에 있다

## 1. 이 문서의 위치

- 결정 기록(`설계_261104_웹 전환 결정 기록`)은 전환의 큰 결정(D-W계열)을 담는다. 이 문서는 구현 마일스톤마다 내린 세부 결정을 이어서 쌓는다 (개발방법론 §2.3 아키텍처 결정 기록, 지속 누적).
- 설계 문서(요구사항, 데이터 모델, API, 화면, 인증·보안, 테스트)는 이 번호를 인용한다. 같은 내용이 GitHub 결정 이슈에도 있다: MW #17, M7 #18, M8 #19, 디자인 #21 (이슈는 이유를 추적하는 곳이고, 되돌아볼 결정은 이 문서에도 남긴다).
- 운영 업체 선정(D-OP08~11)은 배포·운영 설계에 있다 (이슈 #20).

## 2. MW 공용 단어장 (이슈 #17, 요구사항 FR-BOOK-01~06)

회원이 단어를 직접 추가·수정·삭제하고 CSV로 가져오던 방식을, 운영자가 준비한 공용 단어장을 담고 제외하는 방식으로 바꿨다 (사용자 요청 2026-11-05).

| 항목 | 결정 | 고려한 대안 | 이유 |
|------|------|-------------|------|
| D-WB01 단어장 출처 | 운영자가 DB에 넣는 읽기 전용 공용 목록. 테이블 `wordbooks`, `wordbook_entries`, `user_wordbooks` | 외부 사전 API, Quizlet 파일 가져오기 | 시연에 인터넷이 필요 없고 한글 뜻이 있는 단어장을 바로 보여 줌 |
| D-WB02 담기 | 회원의 `words`로 복사 | 항목을 직접 참조 | 진도, 기록, 시험 코드(M5, M6)를 바꾸지 않음. 회원 격리 유지 |
| D-WB03 제외 | 남은 단어장에 없는 단어만 소프트 삭제 | 항상 전부 삭제 | 겹치는 단어 보존. 학습 기록은 남고 다시 담으면 이어 감 |
| D-WB04 회원 기능 | 추가·수정·삭제·가져오기·내려받기 API와 화면 제거. 조회·검색·정렬은 유지 | 화면만 숨김 | 안 쓰는 API가 공격 면으로 남지 않음 |
| D-WB05 등록 방법 | 명령줄 도구 `load_wordbooks.py`와 `data/wordbooks.json` | 관리자 화면 | 관리자 권한 체계가 없음 |
| D-WB06 같은 단어 | 먼저 담은 뜻 유지 | 나중 뜻으로 덮어씀 | 학습 중인 뜻이 바뀌는 혼란 방지 |
| D-WB07 권한 | 담기·제외는 `VerifiedWrite` | - | 회원 데이터 쓰기 규칙 |
| D-WB08 화면 | `/wordbooks`(고르기), `/words`(읽기 전용) | 한 화면 | 역할 분리 |
| D-WB09 샘플 | `data/words.csv`를 구간으로 나눈 "기본 영단어 1~4"(2026-11-05 사용자 요청으로 "초급·중급·고급·심화 단어"로 이름을 바꿨다) | 수능 이름 사용 | 출처 미확인 자료에 수능 이름을 붙이지 않음 |
| D-WB10 기존 데이터 | 변환하지 않음 | - | 운영 전, 시연 DB는 새로 만듦 |
| D-WB11 동시 요청 | 조회를 쓰기 전에 모두 끝내고 commit 오류를 409로 변환 | 쓰는 중 조회 | 자동 flush의 제약 오류가 try 밖에서 500이 되는 것을 테스트가 잡음 |
| D-WB12 테스트 단어 | `insert_words`, `insert_wordbook` 도우미로 DB에 직접 넣음 | 단어 추가 API 유지 | API를 없앴고 시험·진도 코드는 그대로 |
| D-WB13 브라우저 점검 | 운영자 도구로 표본·점검용 단어장을 임시 DB에 넣고 화면에서 담기 | 점검 전용 우회 | 실제 사용 흐름까지 확인 |

**알려진 위험**
- 운영자가 단어장을 고쳐도 이미 담은 회원 단어는 바뀌지 않는다.
- `data/words.csv`의 출처·라이선스를 확인하지 못했다. 시판 수능 단어장은 저작권이 있어 넣지 않았다.
- 이름은 단계(초급·중급·고급·심화)지만 표본 목록은 난이도순이 아니다. 앞 500개는 가장 기본적인 단어이고 뒤로는 주제가 섞여 있다. "목록 순서 기준으로 나눴다"고 설명한다.
- 담기·제외에 요청 횟수 제한이 없다 (M10에서 검토).

## 3. M7 계정 (이슈 #18, 요구사항 FR-AUTH-10~14)

| 항목 | 결정 | 고려한 대안 | 이유 |
|------|------|-------------|------|
| D-M701 시연의 재설정 | 시연(`APP_ENV=demo`)은 메일을 보내지 않는다. 요청은 다른 환경과 같은 `202`를 주고, 재설정 요청 화면에 "시연 환경에서는 메일이 발송되지 않습니다" 안내를 둔다 | 응답이나 화면에 링크를 보여 줌 | 시연 이메일은 가짜 주소라 받을 수 없다. 링크를 보여 주면 이메일만 알면 남의 계정을 바꿀 수 있다 |
| D-M702 재설정 토큰 | `auth_tokens`(purpose `reset_password`), 30분, 한 번만 사용, 링크는 `/reset-password#token=…`(조각이라 접속 로그에 남지 않음). 새 요청은 이전 링크를 무효로 한다 | 쿼리 문자열 | 인증 메일과 같은 방식 (이슈 #9) |
| D-M703 재설정 요청 | 가입 여부와 관계없이 같은 `202`와 문구. 같은 계정 1시간 3회, 같은 IP 1시간 20회. 소셜 전용 계정(비밀번호 없음)도 메일을 보낸다 | 계정만 제한 | 메일 폭탄 방지, 계정 존재 노출 방지 (D-A04) |
| D-M704 재설정 완료 | 비밀번호 규칙 검사 후 변경하고 모든 세션을 종료한다. 메일을 받았으므로 이메일 인증도 완료 처리한다 | 인증은 따로 | 메일 수신을 증명했고, 남의 주소로 가입된 계정의 주인이 되찾는 경로다 (인증 설계 §3.2 위험) |
| D-M705 비밀번호 변경 | 현재 비밀번호 확인, 새 비밀번호 규칙 검사, 현재와 같으면 거절. 성공하면 현재 세션 외 세션 종료. 현재 비밀번호 틀림은 계정당 15분 5회까지 | 제한 없음 | 탈취된 세션으로 비밀번호를 무차별 대입하는 길을 막음 (인증 설계 §5) |
| D-M706 탈퇴 | 비밀번호 확인 + 화면에서 "탈퇴" 입력. 회원 행 삭제(연쇄), 세션 쿠키 삭제, `204`. 같은 이메일로 재가입 가능. 확인 실패는 변경과 같은 제한을 공유 | 유예 기간 | 결정 D-W12 하드 삭제 |
| D-M707 표시 이름·내 정보 | `GET /me`, `PATCH /me`(인증 완료, 가입과 같은 이름 규칙) | - | API 설계 §2 |
| D-M708 모든 기기 로그아웃 | `POST /auth/logout-all`: 현재 세션 포함 전부 종료 | - | 인증 설계 §2.1 |
| D-M709 화면 | `/forgot-password`(P-06), `/reset-password`(P-07), `/account`(A-01), 로그인 화면에 "비밀번호를 잊으셨나요?", 메뉴 "내 계정" | - | 화면 설계 |
| D-M710 소셜 전용 계정 | M8에서 처리. M7은 비밀번호가 없는 계정의 비밀번호 확인을 실패로 취급 | M7에서 선반영 | 소셜 계정이 아직 없음 |

**구현 중 바뀐 결정**
- 탈퇴(D-M706)는 `DELETE /me`가 아니라 `POST /me/delete`다 (API 설계 D-API11). DELETE 본문을 막는 환경이 있다.
- 비밀번호 변경과 탈퇴는 비밀번호를 다시 확인하므로 인증 전 회원도 쓸 수 있다 (API 설계 D-API12). 표시 이름 변경은 인증 완료 회원만 가능하다.
- D-M710은 M8의 D-M808로 이어져 해결했다.

**알려진 위험**
- 시연에서는 비밀번호 재설정을 쓸 수 없다. 로그인한 상태의 변경과 탈퇴는 쓸 수 있다.
- 운영 메일 발송은 M10 전까지 실패 처리라 운영에서 재설정은 M10 이후 동작한다.

## 4. M8 소셜 로그인 (이슈 #19, 요구사항 FR-AUTH-15~17)

사용자 확정: 설계 전체를 구현하고 OAuth 앱은 아직 등록하지 않아 가짜 제공자로 구현·테스트한다.

| 항목 | 결정 | 고려한 대안 | 이유 |
|------|------|-------------|------|
| D-M801 제공자 연동 | 제공자 어댑터(`social_providers.py`)가 인증 주소 만들기와 "코드 → 토큰 → 사용자 정보" 교환을 맡는다. 구글은 OIDC 사용자 정보 엔드포인트, 카카오는 `/v2/user/me`. 토큰은 서버에서만 쓰고 저장하지 않는다. 테스트는 `httpx.MockTransport`와 가짜 제공자 | ID 토큰 서명 검증, 외부 OAuth 라이브러리 | TLS로 제공자에서 직접 받은 사용자 정보를 쓰면 서명 검증이 필요 없고, 직접 구현 방침(D-IMP04)과 맞다. `nonce`는 ID 토큰을 쓰지 않아 필요 없다 |
| D-M802 설정과 켜기 | `GOOGLE_CLIENT_ID/SECRET`, `KAKAO_REST_API_KEY/KAKAO_CLIENT_SECRET`가 있는 제공자만 켠다. 시연(`demo`)에서는 켜지 않는다 | 항상 표시 | 키가 없으면 버튼도 없다. ngrok 무료 주소는 매번 바뀌어 콜백 주소를 등록할 수 없다 |
| D-M803 시작·상태 저장 | 시작 요청마다 `auth_sessions`에 대기 행(`state`, PKCE `code_verifier`, 10분)을 만들고 별도 쿠키 `sv_oauth`(HttpOnly, Lax)로 가리킨다. 콜백은 `state`를 일치 확인 뒤 즉시 지운다 | 로그인 쿠키 `sv_session`에 저장 (설계 §4.5 문구) | 로그인한 회원이 계정 연결을 시작해도 기존 세션 쿠키를 덮어쓰지 않는다. 시작 횟수는 IP당 10분 30회로 제한한다 |
| D-M804 계정 규칙 | 설계 §4.2 그대로: (1) 연결된 소셜 계정이면 로그인, (2) 제공자가 인증된 이메일을 주고 같은 이메일 회원이 있으면 연결 후 로그인, (3) 인증된 이메일인데 회원이 없으면 인증 완료 회원을 만들어 로그인(제공자가 이미 이메일을 확인했으므로 인증 메일을 생략), (4) 이메일이 없거나 미인증이면 가입 대기 | 항상 인증 메일 | 제공자 인증 이메일은 소유 증명이다 |
| D-M805 선점 계정 방어 | 규칙 2에서 기존 회원이 이메일 미인증이었다면 비밀번호를 지우고 모든 세션을 끝낸 뒤 인증 완료로 바꾼다 | 그대로 연결 | 남의 이메일로 먼저 가입해 둔 공격자가 비밀번호를 쥔 채 계정이 넘어오는 것을 막는다 |
| D-M806 이메일 없는 가입 | 가입 대기 행에 제공자 번호·이름을 두고, `POST /auth/social/complete`로 이메일을 받아 인증 메일을 보낸다. 인증 링크를 누르면 회원을 만들고 소셜 계정을 연결한다(자동 로그인 없이 소셜 로그인으로 들어옴). 이미 가입된 이메일이면 "이미 가입" 안내 메일만 보내고 응답은 같다 (D-A04). 인증 토큰은 대기 행에 해시로 저장해 `auth_tokens`를 바꾸지 않는다 | `auth_tokens`에 대기 행 연결 | 인증이 끝나야 회원을 만든다는 설계(D-W13)를 지키며 스키마 변경을 줄인다 |
| D-M807 연결·해제 | 연결: `POST /auth/social/{p}/link`가 비밀번호를 확인(있는 계정만)하고 인증 주소를 돌려준다. 콜백이 연결을 마친다. 해제: `DELETE /auth/social/{p}`, 비밀번호가 없고 마지막 연결이면 `409 LAST_LOGIN_METHOD`. 설계의 P-08은 별도 화면 없이 내 계정의 연결 버튼으로 둔다 | 별도 P-08 화면 | 로그인한 상태가 이미 비밀번호 확인이다. 하이재킹된 세션이 소셜 계정을 몰래 붙이지 못하게 연결 전에 비밀번호를 다시 확인한다 |
| D-M808 소셜 전용 계정 | 비밀번호 변경은 현재 값 없이 새 비밀번호를 설정할 수 있다. 탈퇴는 비밀번호를 먼저 설정해야 한다 | 제공자 재로그인으로 탈퇴 확인 | 제공자 재로그인 확인은 별도 흐름이 필요하고 이번 범위의 가치가 작다. 비밀번호 설정 뒤 기존 탈퇴 흐름을 쓴다 |
| D-M809 스키마 | 마이그레이션 `0003`: `auth_sessions`에 `oauth_state`, `oauth_code_verifier`, `oauth_link_user_id`, `pending_email`, `pending_token_hash` 추가 (모두 비어 있어도 됨) | 새 테이블 | 대기 상태가 이미 이 테이블에 있다 (데이터 모델 §3.10) |

**구현 중 정리한 점**
- 소셜 가입에는 별도 동의 화면이 없다. 버튼 아래 문구("처음 로그인하면 이용약관과 개인정보 처리방침에 동의한 것으로 봅니다")로 갈음하고 가입 시각을 기록한다. 약관 페이지(M10) 전에 동의 화면을 따로 두는 것이 안전하다.
- 틀린 `state`는 시도 한 번으로 대기 행을 지워 값을 맞춰 보는 길을 막는다.
- 같은 제공자의 두 번째 계정은 한 회원에게 연결하지 못한다 (`taken`).
- 인증 메일 링크가 소셜 가입 대기의 것이 아니면 기존 이메일 인증으로 처리한다.

**알려진 위험** (실제 구글·카카오 확인 전)
- 실제 구글·카카오 호출은 등록 전이라 확인하지 못한다. 어댑터는 문서 기준 구현과 모의 전송 테스트만 했다.
- 카카오가 이메일 인증 여부를 알려 주는 조건은 공식 문서로 확인해야 한다 (인증 설계 §4.3 미확인). 보수적으로 `is_email_valid`와 `is_email_verified`가 모두 참일 때만 인증된 이메일로 본다.
- 카카오의 PKCE 지원은 문서로 확인하지 못했다. 보내되 응답이 거절되면 실제 등록 뒤 조정한다.
- 시연에서는 소셜 로그인을 쓰지 않는다.
