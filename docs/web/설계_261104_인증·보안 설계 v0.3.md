**작성일**: 2026-11-04
**버전**: v0.3 (M3 구현 반영)
**설명**: 회원가입·로그인·소셜 로그인, 세션, 토큰, 요청 보호, 개인정보 처리의 기준을 정리한 3단계 설계 문서

## 1. 전제

- 결정 기록 v0.1: FastAPI 백엔드, 이메일·비밀번호와 소셜 로그인 병행, 공개 인터넷 서비스 (D-W01~D-W05).
- 데이터 모델 v0.1: `users`, `social_accounts`를 사용. 이 문서에서 필요한 테이블을 추가하며, 데이터 모델 v0.2에 반영한다 (§8).
- 보안 기준은 OWASP ASVS와 OWASP Top 10을 참고하되, 학습 서비스 규모에 맞춰 필요한 항목부터 적용한다.
- 공개 서비스이므로 "나중에 고친다"가 아니라 **처음부터 막아 둘 항목**과 **단계적으로 넣을 항목**을 나눈다 (§7).

## 2. 세션 방식

| 방식 | 장점 | 단점 |
|------|------|------|
| 서버 세션 (DB 저장, 쿠키에 무작위 값) | 강제 로그아웃·탈퇴 시 즉시 무효화 쉬움 | 요청마다 DB 조회 |
| JWT (서명된 토큰) | 서버 저장 없음 | 발급 후 취소가 어려움 |

**결정 (D-A01)**: 서버 세션을 쓴다. 학습 서비스는 요청량이 적어 DB 조회 비용이 작고, 비밀번호 변경·탈퇴·기기 로그아웃을 즉시 반영할 수 있어야 한다.

### 2.1 세션 규칙

- 쿠키 이름: `sv_session` (예시). 속성은 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`.
- 쿠키 값은 무작위 256비트 값이며, DB에는 **해시만** 저장한다 (D-A02).
- 유효 기간: 절대 만료 14일, 활동 없으면 3일 후 만료 (슬라이딩). 값은 예시이며 확정 필요.
- 로그인 성공 시 새 세션을 발급한다 (세션 고정 공격 방지).
- 세션 종료 범위 (2차 검토 확정):
  - 비밀번호 변경: 현재 세션을 제외한 나머지 세션을 종료한다 (API `POST /me/password`와 일치).
  - 비밀번호 재설정, 탈퇴, "모든 기기 로그아웃": 현재 세션을 포함해 전부 종료한다.
- `last_seen_at`은 1분에 한 번만 저장한다. 만료 기준이 며칠 단위라 오차가 문제되지 않고 쓰기 부하가 줄어든다.
- CSRF 토큰은 세션 값을 키로 한 HMAC-SHA256으로 파생하고, DB에는 그 해시만 저장한다 (D-A10).

### 2.2 `auth_sessions` 테이블 (추가)

| 열 | 타입 | 필수 | 설명 |
|----|------|------|------|
| id | 정수 | O | 기본 키 |
| user_id | 정수 | X | `users.id` (회원 삭제 시 함께 삭제). 소셜 가입 대기 상태에서는 비어 있음 (데이터 모델 v0.2 §3.10) |
| token_hash | 문자열 | O | 세션 값의 SHA-256 해시. 유일 |
| created_at | 일시 | O | 발급 시각 |
| last_seen_at | 일시 | O | 마지막 요청 시각 (슬라이딩 만료 계산) |
| expires_at | 일시 | O | 만료 시각 |
| user_agent_hash | 문자열 | X | 기기 구분용. 원문 대신 해시. 쓰는 기능이 없어 M2에서는 채우지 않는다 (최소 수집) |
| csrf_token_hash | 문자열 | O | CSRF 토큰 해시. 세션마다 발급 (API 설계 §1.2). 데이터 모델 v0.2 §3.10 |

## 3. 이메일·비밀번호

### 3.1 비밀번호 저장 (D-A03)
- 해시 알고리즘: **argon2id** (`argon2-cffi` 패키지). 파라미터는 패키지 기본값을 쓴다 (개발 PC에서 해시 1회 약 65ms). 운영 서버에서 M10에 다시 측정한다.
- 원문 비밀번호는 로그·응답·DB 어디에도 남기지 않는다.
- 대안: bcrypt (널리 쓰이지만 입력 72바이트 제한이 있음). argon2id를 기본으로 한다.

### 3.2 비밀번호 규칙
- 길이 8자 이상, 최대 128자 (긴 문장형 비밀번호 허용).
- 이메일 주소를 포함하면 거절한다.
- 자주 쓰이는 비밀번호 목록(예: 상위 흔한 목록)과 비교한다. M2는 직접 고른 소량의 내장 목록(`security/common_passwords.py`)으로 시작하고, 공개 전(M10)에 공개된 큰 목록으로 교체를 검토한다.
- 조합 규칙(대소문자·기호 강제)은 두지 않는다. 길이 기준이 조합 규칙보다 효과적이라는 입장이다.

### 3.3 이메일 정규화
- 저장과 비교는 소문자 + 앞뒤 공백 제거. 데이터 모델의 `users.email` 규칙과 일치시킨다.
- Gmail 점(`.`)·기호(`+`) 같은 제공자별 규칙은 적용하지 않는다 (중복 가입 방지 목적 외에는 불필요).

### 3.4 가입과 이메일 인증 (열린 질문 3번과 연결)
- 가입 시 `users.email_verified_at`을 비워 두고 인증 메일을 보낸다.
- 인증 전에도 로그인은 허용하되, 단어장 편집 등 쓰기 기능은 인증 후에만 허용한다 (제안).
  - 대안: 인증 전 로그인 자체를 막는다 (더 엄격, 메일이 안 오면 아예 못 쓴다).
- 인증 메일 링크 유효 시간 24시간, 한 번만 사용. 형식은 `{PUBLIC_BASE_URL}/verify-email#token=...`이고 화면 스크립트가 POST로 확인한다 (D-A11).
- 가입 시 이메일은 필수다 (데이터 모델 v0.2 D-W13). 소셜 가입에서 제공자가 이메일을 주지 않으면 이메일 입력 단계를 거친다 (데이터 모델 v0.2 §4.3).
- 가입 응답은 중복 여부와 관계없이 같아야 한다 (D-A04). 자동 로그인도 하지 않는다.

### 3.5 `auth_tokens` 테이블 (추가, 이메일 인증·비밀번호 재설정 공용)

| 열 | 타입 | 필수 | 설명 |
|----|------|------|------|
| id | 정수 | O | 기본 키 |
| user_id | 정수 | O | `users.id` |
| purpose | 문자열 | O | `verify_email` / `reset_password` |
| token_hash | 문자열 | O | 링크 값의 SHA-256 해시. 유일 |
| expires_at | 일시 | O | 인증 24시간, 재설정 30분 (제안) |
| used_at | 일시 | X | 사용된 시각. 값이 있으면 재사용 거절 |
| created_at | 일시 | O | 발급 시각 |

- 같은 회원에게 같은 용도의 미사용 토큰이 있으면 새로 발급할 때 이전 것을 무효화한다.

### 3.6 비밀번호 재설정 (D-A04)
- 재설정 요청 화면은 **가입 여부와 관계없이 같은 문구**를 보여준다 (계정 존재 여부 노출 방지).
- 재설정 완료 시 해당 회원의 세션을 전부 삭제한다.
- 소셜 전용 계정(`password_hash` 없음)은 로그인한 상태에서 현재 비밀번호 없이 새 비밀번호를 설정할 수 있다 (API `POST /me/password`). 재설정 메일로도 만들 수 있다. 계정 설정 화면에서 연결 상태를 보여준다.

## 4. 소셜 로그인

### 4.1 방식 (D-A05)
- **OAuth 2.0 Authorization Code + PKCE**를 쓴다. 서버가 인증 코드를 토큰으로 바꾸고, 브라우저에는 토큰을 노출하지 않는다.
- `state`로 요청 위조를 막고, OpenID Connect를 쓰는 제공자는 `nonce`로 재전송을 막는다.
- 제공자 쪽에서 받는 값은 고유 사용자 번호(`sub`)와 이메일, 이메일 인증 여부, 이름으로 한정한다 (최소 수집).

### 4.2 계정 연결 규칙 (D-A06)
1. 이미 `(provider, provider_user_id)`가 있으면 그 회원으로 로그인한다.
2. 없고, 제공자가 **이메일 인증됨**을 알려주며 같은 이메일의 기존 회원이 있으면 그 회원에 연결한다.
3. 없으면 가입 대기 상태로 둔다. 제공자가 준 이메일이 있으면 그 주소로 인증 메일을 보낸다. 이메일이 없으면 이메일 입력 단계를 거친다 (데이터 모델 v0.2 §4.3). 인증이 끝나야 회원을 만든다 (`password_hash` 비움).
4. 이메일이 인증되지 않았거나 제공자가 알려주지 않으면, 기존 회원과 자동 연결하지 않는다. 로그인 후 "계정 연결" 화면에서 비밀번호로 확인하고 연결한다.

- 규칙 2를 엄격하게 두는 이유: 이메일 인증이 안 된 소셜 계정으로 다른 사람의 계정에 들어가는 것을 막기 위해서다.

### 4.3 제공자 선정 (열린 질문)
- **확정 (사용자 답변)**: 구글, 카카오. 네이버는 이번 범위에서 제외한다.
- 카카오는 이메일을 선택 동의로 받는다. 이메일을 주지 않으면 이메일 입력 단계로 보낸다 (데이터 모델 v0.2 D-W13). 카카오가 이메일 인증 여부를 알려주는 조건은 공식 문서로 확인해야 한다 (미확인).

### 4.4 `social_accounts` 보완
- 데이터 모델 v0.1의 `social_accounts`에 `email_at_link` (연결 당시 제공자 이메일, 참고용)을 추가한다. 연결 기준은 `provider_user_id`이므로 이메일이 바뀌어도 로그인은 유지된다.

### 4.5 OAuth state와 PKCE 값 (2차 검토 추가)
- 시작 요청(`GET /auth/social/{provider}/start`)마다 `state`와 PKCE `code_verifier`를 만든다. 두 값은 **가입·로그인 대기 세션**(데이터 모델 v0.2 §3.10 `auth_sessions`의 대기 상태)에 해시가 아니라 원문으로 저장한다. 제공자에게 보내는 값은 `code_challenge` (verifier의 해시)뿐이다.
- 만료: 시작 후 10분. 만료되면 콜백은 실패하고 다시 시작하게 한다.
- 일회성: 콜백에서 `state`가 맞으면 대기 값을 즉시 지운다. 같은 `state`로 두 번째 콜백이 오면 거절한다 (재사용 방지).
- 콜백의 `state`가 세션의 값과 다르면 거절하고 로그인 화면으로 보낸다 (요청 위조 방지).
- 보안 테스트 항목: 만료된 `state`, 재사용된 `state`, 다른 세션의 `state`를 모두 거절하는지 확인한다 (작업계획 §7).

## 5. 요청 보호

| 위협 | 대응 |
|------|------|
| CSRF (상태 변경 요청 위조) | `SameSite=Lax` 쿠키 + 로그인 후 상태 변경 요청(POST/PUT/DELETE)에 CSRF 토큰 헤더 요구 (D-A07). 세션이 없는 공개 POST는 `application/json`만 받는다 (D-A12) |
| XSS (화면에 스크립트 삽입) | 템플릿 자동 이스케이프, 사용자 입력 HTML 금지, CSP 헤더 (`script-src 'self'`) |
| 무차별 대입 (로그인 시도) | 계정+IP 조합 15분 5회 실패 시 잠금 + IP 기준 15분 50회 제한 (D-A08, §5.1) |
| 계정 존재 노출 | 가입·재설정 응답 문구 통일, 응답 시간 차이 최소화 |
| 권한 우회 (남의 단어장 접근) | 모든 조회·수정 쿼리에 `user_id` 조건 필수. 다른 회원 자원은 `404`로 응답 (D-A09) |
| CSV 파일 공격 | 가져오기 파일 5MB, 5,000행 이하. 내보내기 때 `=`, `+`, `-`, `@`, 탭, CR로 시작하는 값에 `'` 접두 (CSV 수식 주입). 가져올 때 접두를 되돌린다 (API 설계 D-API09). 요청 전체 크기는 프록시에서 제한한다 (FastAPI가 인증 확인 전에 본문을 읽음) |
| 과도한 요청 (2차 검토 확장) | 아래 대상에 요청 횟수 제한 (`login_attempts` 방식 재사용, 데이터 모델 v0.2 §3.12) |

요청 횟수 제한 대상 (2차 검토):
- 로그인 (계정 기준 + IP 기준)
- 인증 메일: 가입과 재발송을 합쳐 같은 주소 1분에 1회. 가입 직후 재발송으로 제한을 우회하지 못하게 한다
- 가입: 같은 IP 1시간에 20회. IP를 공유하는 학교 같은 곳을 고려해 넉넉하게 둔다
- 비밀번호 재설정 요청 (메일 폭탄 방지, 같은 이메일 1시간에 3회 제안)
- 비밀번호 재설정 확인, `POST /me/password`, `DELETE /me`, `POST /auth/social/{provider}/link` (비밀번호 재확인 값 무차별 대입 방지)
- CSV 가져오기 (`POST /words/import`): 회원당 1시간 20회. 잘못된 파일도 횟수에 센다
| 전송 도청 | HTTPS 강제, HSTS 헤더. 쿠키 `Secure` |
| 클릭재킹 | `X-Frame-Options: DENY` 또는 CSP `frame-ancestors 'none'` |

### 5.1 로그인 시도 제한 저장 (D-A08)
- MVP는 DB 테이블 `login_attempts`(계정·IP 해시·시각)로 센다. 서버를 여러 대로 늘리면 메모리 방식은 쓸 수 없으므로 DB 방식을 기본으로 한다.
- 계정과 IP 값은 HMAC-SHA256 + 서버 키 `AUTH_HASH_KEY`로 해시한다. 경우의 수가 작은 값이라 키 없는 해시는 쉽게 되돌릴 수 있다 (D-A13).
- 없는 이메일의 실패도 같은 방식으로 세어, 잠금 여부로 가입 여부가 드러나지 않게 한다. 잠금 판정은 비밀번호 검증보다 먼저 하므로 잠금 중에는 맞는 비밀번호도 `429`다.
- 판정과 기록 사이에 틈이 있어 동시 요청은 제한을 약간 넘을 수 있다. 단일 서버 규모에서는 허용한다. 여러 IP를 쓰는 공격은 조합 기준을 피할 수 있다. 피해자 계정 잠금 방지를 택한 결과다.
- 실패 기록은 성공 시 해당 계정 기준으로 지우고, 보관 기간(30일) 지나면 삭제한다 (데이터 모델 v0.2 §3.12).
- **계정 단위 잠금의 약점 (2차 검토)**: 계정만 기준으로 잠그면 제3자가 피해자 계정을 일부러 잠글 수 있다. 그래서 잠금 판정은 **계정과 IP를 함께** 본다. 같은 계정이라도 실패가 많은 IP만 잠그고, 다른 IP의 로그인은 막지 않는다 (구현 시 세부 임계값 조정).
- 잠금 중 응답: `429 RATE_LIMITED`, 응답 본문에 `retry_after`(초)를 넣는다 (API 설계 §1.3).

## 6. 개인정보 처리 (공개 서비스 요구)

- **수집 항목 최소화**: 이메일, 표시 이름, 비밀번호 해시(또는 소셜 고유 번호). 학습 기록은 서비스 제공에 필요한 범위만 저장한다.
- **동의 기록**: `users`에 `terms_agreed_at`, `privacy_agreed_at` 추가. 가입 때 이용약관·개인정보 처리방침 동의를 받고 시각을 남긴다.
- **IP 주소**: 원문을 저장하지 않는다. 로그인 시도 기록에만 해시로 남기고 보관 기간을 둔다.
- **로그**: 비밀번호, 세션 값, 인증 토큰, 소셜 토큰은 기록하지 않는다. 인증 성공·실패와 탈퇴 같은 이벤트만 남긴다.
- **탈퇴 (D-W12 하드 삭제)**: 탈퇴 즉시 세션 삭제 + 회원 데이터 삭제(단어, 설정, 진도, 기록, 시험, 소셜 연결). 삭제 순서는 데이터 모델 v0.2 §4.4. 백업에 남은 데이터는 보관 기간 후 자동 소멸한다고 처리방침에 명시.
- **이메일 재사용**: 탈퇴 후 데이터가 삭제되면 같은 이메일로 다시 가입할 수 있다 (확정).
- 개인정보 처리방침과 약관 문안은 별도 문서로 작성한다 (배포 설계 단계 이전에 필요).

## 9. 설계 결정 (ADR 형식)

### D-A01 세션 방식: 서버 세션
- **대안**: JWT. 취소가 어렵다는 점이 공개 서비스의 탈퇴·비밀번호 변경 요구와 맞지 않아 제외.

### D-A02 세션 값은 해시로 저장
- **근거**: DB가 유출돼도 세션 값으로 바로 로그인할 수 없다.

### D-A03 비밀번호 해시: argon2id
- **대안**: bcrypt. 기능은 충분하지만 72바이트 입력 제한이 있어 제외.

### D-A04 재설정·가입 응답 통일
- **근거**: 계정 존재 여부가 드러나면 개인정보 노출 문제가 된다.
- **적용 (v0.2)**: 가입은 중복이어도 같은 응답(`202`)을 주고 자동 로그인하지 않는다. 신규면 인증 메일, 기존 회원이면 "이미 가입된 이메일입니다" 안내 메일을 보낸다. 쿠키 발급 여부로도 존재가 드러나지 않게 한다.

### D-A05 소셜 로그인: Authorization Code + PKCE
- **대안**: Implicit 흐름 (토큰이 브라우저에 노출되어 현재 권장되지 않음). 제외.

### D-A06 소셜 계정 자동 연결은 이메일 인증 확인 시에만
- **근거**: 미인증 이메일로 자동 연결하면 계정 탈취가 가능하다.

### D-A07 CSRF: SameSite + 토큰 헤더
- **근거**: 쿠키 속성만으로는 오래된 브라우저와 일부 요청 경로를 막기 어렵다. 이중 방어로 둔다.

### D-A08 로그인 제한은 DB에 기록
- **대안**: 메모리 카운터. 서버가 여러 대가 되면 제한이 깨짐. 초기 단일 서버에서도 재시작 때 초기화되지 않도록 DB를 쓴다.

### D-A09 다른 회원 자원은 404
- **근거**: 403을 쓰면 해당 번호의 자원이 존재한다는 정보가 새어 나간다.

### D-A10 CSRF 토큰은 세션에서 파생 (v0.2)
- **배경**: `GET /auth/session`은 토큰을 돌려줘야 하는데 DB에는 해시만 저장한다.
- **대안**: 원문 저장 (DB 유출 시 함께 노출), 조회마다 새 토큰 (여러 탭에서 먼저 연 탭의 토큰이 무효가 됨).
- **결정 근거**: 세션 값을 모르면 계산할 수 없고, 저장 없이 같은 토큰을 다시 돌려줄 수 있다.

### D-A11 인증 토큰은 URL 조각에 두고 POST로 확인 (v0.2)
- **배경**: 쿼리 문자열은 접속 로그에 남는다 (배포 설계 §6.1). GET으로 소비하면 메일 검사 프로그램이 링크를 미리 열 때 인증이 끝난다.
- **대안**: 쿼리 문자열 + 로그 마스킹 (빠뜨릴 곳이 많음).
- **결정 근거**: URL 조각은 서버로 전송되지 않는다. 링크의 기준 주소는 조작 가능한 Host 헤더 대신 `PUBLIC_BASE_URL`을 쓴다.

### D-A12 로그인 전 요청은 JSON만 허용 (v0.2)
- **배경**: 세션이 없으면 CSRF 토큰을 줄 수 없다. 로그인 위조를 막아야 한다.
- **대안**: 로그인 전 임시 토큰과 쿠키 발급 (구조가 복잡해짐).
- **결정 근거**: 다른 사이트의 폼은 JSON을 보낼 수 없고, `fetch`는 브라우저의 사전 확인에서 막힌다. 테스트로 고정했다.

### D-A13 이메일·IP는 키를 쓴 해시 (v0.2)
- **대안**: 일반 SHA-256 (IPv4 전체 계산이나 이메일 목록 대입으로 되돌릴 수 있음).
- **결정 근거**: 처리방침의 "IP 원문 미저장" 취지를 지킨다. 키를 바꿔도 시도 기록만 초기화되어 교체 부담이 작다.
